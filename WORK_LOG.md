### 1. The cost model of the native backend (the finding that drove the rest)

Five primitives measured on both sides with `benchmarks/micro.bend` /
`benchmarks/native/micro.c` (`tools/costmodel.py`, report in
`build/performance/costmodel.json`, table in `BENCHMARKS.md`). On this machine:

| primitive | what it is | bend | ref | ratio |
|---|---|---|---|---|
| `arith` | one LCG step and an add | 1.40 ns | 1.54 ns | 0.91x |
| `array` | one indexed read + write of a 4096-slot `Base.Array` | 1.55 ns | 1.46 ns | 1.06x |
| `list`  | one step of traversing a **retained** (`&2`) cons list | 9.03 ns | 1.05 ns | 8.62x |
| `alloc` | one node of a built-and-consumed binary `Data` tree | 2.64 ns | 22.17 ns | 0.12x |
| `fresh` | one node of a built-and-consumed (`&2`) cons list | 10.89 ns | 16.50 ns | 0.66x |

This does not say what one might expect, and it corrected my own working
hypothesis twice:

* Arithmetic and **indexed `Base.Array` access are at parity with C**. Bend
  compiles `Array.get`/`Array.set` to real indexed loads and stores on a flat
  array, and `Nat`, `U32.from_nat`/`to_nat` and `Nat.div` to machine
  arithmetic. (`Nat` is `Zero | Succ` in the *type theory*; the backend does
  not evaluate it unarily. I had assumed the opposite and measured it.)
* **Allocation is not the problem**: a plain `Data` tree node costs ~2.6 ns to
  allocate, traverse and release.
* **Traversing a retained, shareable (`&2`) structure is the problem**: ~9 ns
  per node against ~1 ns in C, because the runtime duplicates the part it
  consumes. Every persistent structure in this library is built from `&2`
  types, so every traversal pays it.

The two C rows that look bad for C (`alloc`, `fresh`) are malloc/free per
node; an arena would be several times faster, so they are recorded as
absolute Bend costs, not as Bend wins.

Consequence for the 2.5x contract: a structure whose operations are indexed
array accesses **can** meet it; a structure whose operations walk retained
`&2` nodes **cannot**, no matter how the code is tuned. That is a
representation question, not a tuning question, and it is now backed by
measurements rather than by argument.

### 2. bitset: migrated from a list of words to a native Base.Array

`src/bitset.bend` stored its words in a `List<&2, U32>`, which made `get`,
`set` and `clear` O(words) while the C reference is O(1) on a flat array -
not the same algorithm, and the reason those rows were the worst in the
suite (`bitset.set` / medium was **2243x**). It now stores them in a
`Base.Array` of 2^depth words, addressed by `i / 32` and `i % 32`.

Measured after the change (same harness, same C reference):

| row | before | after (measured, this iteration's report) |
|---|---|---|
| `bitset.set` medium | 2243.44x | **1.13x** |
| `bitset.clear` medium | 2079.05x | **1.00x** |
| `bitset.get` medium | 587.51x | **1.33x** |
| `bitset.union` medium / large | 22.34x / n/a | **0.97x / 0.95x** |
| `bitset.intersection` medium / large | 22.62x / n/a | **1.05x / 0.99x** |
| `bitset.difference` medium / large | 22.49x / n/a | **0.96x / 0.88x** |
| `bitset.xor` medium / large | 22.08x / n/a | **1.18x / 0.91x** |
| `bitset.new` small / medium / large | 1.32x / n/a / n/a | 2.46x / 2.98x / 3.22x |
| `bitset.count` medium | 17.06x | 16.73x |
| `bitset.to_list` medium | 4.76x | 4.53x |
| structure median over all its rows | 9.50x | **1.24x** |
| rows within 2.5x | 3 of 31 measured | **25 of 44** |
| rows that could not be measured at all | 12 | **0** |

(`n/a` = the row could not be measured at all before: the list-backed
implementation was too slow to finish a `large` workload inside the per-row
budget.)

`new` got *slower* in relative terms (1.32x -> 2.46x at size 64, 3.22x at
262144): it now runs `depth_for`, a loop of up to 31 steps, where the list
version did nothing. Caching the depth is the obvious fix and is the one
bitset row that is still over the limit for a reason that is pure constant
factor rather than algorithm.

`count` and `to_list` are still 13-16x and 4-6x: both walk 32 bits per word
with the same shift-and-add loop the C reference uses, and clang vectorises
that loop. A provable SWAR popcount is the open item there.

`Base.Array` is linear, so `Bitset` became a `Type`: every operation returns
the bitset, `dispose` releases one, `clone` makes two independent copies, and
the binary operations return **both** operands (a linear API has to give back
what it borrowed). The trace runner's binary operations compare the logical
sizes before building the operand bitset, which is both faster and what makes
the refinement unconditional (see below).

Proofs, all re-established from scratch against the new representation and all
checked:

* `proofs/bitset/index.bend` - `i / 32` and `i % 32` peel 32 bits at a time.
  Base's `Nat.divmod.go` is a structural recursion on the dividend, so 32
  unfoldings of `Nat.add(32n, i)` are a *definitional* step; only the quotient
  accumulator needs an induction.
* `proofs/bitset/walk.bend` - the word-list walks of the old implementation
  (kept as the proof model in `proofs/bitset/model.bend`) are exactly one
  indexed access.
* `proofs/bitset/arr.bend` - `Base.Array` get/set against the slot list, on
  the existing `proofs/lib/array.bend`.
* `proofs/bitset/listx.bend`, `loops.bend`, `zip.bend` - the three whole-array
  loops (`count_go`, `members_go`, `zip_go`) compute exactly what the list
  model says.
* `proofs/bitset/depth.bend` - the depth `depth_for` picks is below 32.
* `proofs/bitset/state.bend`, `steps.bend`, `trace.bend` - abstraction,
  invariant and shadow (the `proofs/dynamic_array` style, because the array is
  linear), every operation including every error path, `from_bools`, and
  arbitrary finite traces.

The independent specification `spec/bitset.bend` and all of the
Boolean-sequence mathematics (`proofs/bitset/lists.bend`, `word.bend`) are
untouched: the model never mentioned the representation.

**Honest narrowing.** The packed array has a capacity: the depth is capped at
31, i.e. 2^31 words = 2^36 bits, so that every word index is a representable
U32. The laws about `new(n)` therefore carry an explicit premise that `n` fits
(`proofs/bitset.bend` `capacity`). `step_ok` and the trace law from any
invariant-satisfying state are unconditional, and the invariant implies the
premise. The old list-of-words representation had no capacity bound; this is
the price of O(1) indexed access and it is the same bound
`benchmarks/native/bitset.c` has. It is the same kind of documented bound
`src/dynamic_array.bend` already carried.

Two of the bitset mutants in `tools/mutants.py` were rewritten (their sites no
longer exist) and two were added; one candidate mutant was *rejected* during
this work because it turned out to be semantically equivalent (removing the
early size check in `comb_bits` still leaves the inner check, so nothing
observable changes) - the suite correctly reported it as surviving.

### 3. Measurement: the batch now grows in `count`, not only in `reps`

`benchmarks/run.py` could only lengthen a measurement by repeating whole
rounds, and a round includes building the structure. For a large structure
with a cheap operation the build dominated, so the difference `A - B` could
never be driven above the clock minima and the row was reported as a FAILED
measurement: 84 of 408 rows.

Operations are now classified in `benchmarks/workloads.py` as size-preserving
or size-changing. A size-preserving operation is repeated more times *inside*
one round, so the build is paid once per round instead of once per batch; a
size-changing operation can still only repeat whole rounds, because a longer
batch would no longer be that operation at that size. The classification is
recorded per row in the report (`grow`).

Nothing about the integrity rules changed: no clamping, no floors, the same
minima on both sides, and a row that still cannot be driven above them is
still a FAILED measurement and never a ratio.

A residual class of failures is now understood and documented rather than
merely reported: for a *destructive sweep* (`pop`, and the same shape
elsewhere) region A ends with an empty structure and region B with a full one,
so the two regions do not pay the same deallocation cost and `A - B` can come
out negative. That is a real asymmetry of the two-region design for
destructive operations, not noise.

### 6. union_find: migrated to three parallel Base.Array arenas

The measured cost model says the two things wrong with the old
`V.Vec<Cell>` representation:

* a **wide** record costs per field when it is read out of an array - a
  scratch measurement put a 3-field `Cell` read at 6.5 ns against 1.5 ns for
  a 1-field read - so every `find` paid for the size and member fields it
  never looked at;
* the `Vec` was a retained `&2` tree walked by pattern matching, the one
  primitive the cost model puts at ~8.6x C.

`src/union_find.bend` now keeps three narrow arenas - `Array<Nt>` roots,
`Array<Nt>` sizes, `Array<Ms>` member lists - all of depth `depth_for(n)`,
each read with `Array.get` and written with `Array.set` at a `U32` index.
`union` relinks the smaller class through its member list (eager full
compression), so `find` is a single indexed read. Measured against the same
C algorithm: `find` 0.94x, `connected` 1.11-1.37x, `component_size`
1.01-1.12x, `component_count` 0.35x.

The proof migration kept the mathematics and replaced only the bridge:

* `proofs/union_find/cells.bend` (new) holds the proof-level `Cell` and the
  **zip** `cells(roots, sizes, members)` that turns the three slot lists into
  the one cell list the old proofs talk about;
* `proofs/union_find/model.bend` (303 lines) and `union.bend` (513 lines) -
  the partition mathematics, `good2`, `labs_relabel`, `fix_count` - survived
  unchanged apart from that rename;
* `proofs/union_find/arr.bend` (new) relates `Base.Array` get/set to the slot
  lists, `bridge.bend` (new) proves the one equation
  `cells(rlr(ms, roots, big), sizes, members) == rl(ms, cells(...), big)` that
  lets the retained `union.bend` apply to the new representation;
* `state.bend` defines the shadow `Sh{n, d, tr, tz, tm, c}`, `real`, `good`,
  `model`, the projections and `real_inj` (a live structure determines its
  shadow, so the laws cannot be satisfied by naming a different one);
* `steps.bend` proves `step_ok` for all five operations in the shadow Sigma
  form, `init.bend` proves the constructor's shadow is good and its model is
  `iota`, and `trace.bend` is the bitset trace proof verbatim modulo names.
* `proofs/union_find.bend` and the `union_find` laws in `END_TO_END.bend` are
  restated in the shadow form; `bend PROOF.bend` re-checks the whole closure.
* `tools/mutants.py` has seven union_find mutants against the new source
  (tie-break flipped, count not decremented, an existing class reported as
  changed, the merged size slot off by one, `relink` skipping a member, the
  merged member list dropping the small class, `component_size` reading slot
  0); `tools/validate.py --only union_find` passes runtime, boundaries,
  differential, mutations and trace_proof.

The replaced sources are in `docs/archive/` with a README entry saying what
carried over and what the replacement cost (the arena capacity premise on
`new`).

### 7. Benchmark harness: three regions and an alternated region order

Two defects of the two-region A/B form showed up as 21 FAILED rows and as
`A - B` coming out *negative* by hundreds of milliseconds:

1. **Deallocation asymmetry.** Region A ended with a structure the measured
   operations had emptied or grown; region B ended with the one the build left
   behind. The two regions did not pay the same destruction cost, and at
   `large` sizes that difference was bigger than the signal.
2. **Region-order drift.** Whatever runs last on a machine that is scaling its
   clock looks slower. Timing A then B in one process turns that drift into a
   systematic bias of exactly the shape `A - B` measures.

Both sides now run three regions per process - `A = reps x round(2k ops)`,
`B = reps x round(k ops)`, `C = reps x round(no ops)` - and `argv[5]` selects
whether they run `ABC` or `CBA`; `benchmarks/run.py` alternates that over the
samples and reports medians. `A - B` is exactly `k x reps` operations with the
build, the settle and the destruction cancelling, and both regions end in a
state the operation has been applied to, so the deallocation of what the extra
`k` operations removed is *inside* the difference, where it belongs (the C
reference's `free()` is inside its own). `C` is the build-and-destroy control
and is recorded for every row (`bend_control_ns`, `reference_control_ns`).

An intermediate design that subtracted `k` value-stream steps (`B = k ops +
k null steps`) was tried and **rejected on evidence**: measured on the C
reference, the null step (LCG + checksum fold behind the DoNotOptimize
barrier) costs ~7 ns while `uf_find` costs ~4.9 ns, so the subtraction drove
the reference delta negative. The filler is kept in the drivers (the `kn`
parameter) but no region uses it.

A useful side effect: an operation whose result Bend's interaction net shares
across the loop can no longer be reported as a number. Region A runs the loop
`2k` times and region B `k` times, so a shared result makes them cost the same
and the row FAILS as unmeasurable. The `argument-free` flag is kept as a
pointer to the rows where that is the thing to check.

### 7b. What the three-region form fixed, and what it did not

Fixed, with evidence in `build/bench/logs/samples.log`:

* the region-order bias (every row's samples now alternate `ABC`/`CBA`, and
  the per-order numbers agree where they previously did not);
* the aggregate deallocation asymmetry: regions A and B free the same total
  number of elements, so a destructive operation no longer moves whole-round
  deallocation work out of the difference;
* the saturating destructive sweep: `sized()` rows now use `count = size / 2`,
  so region A is exactly the full sweep and region B its first half. Region A
  can no longer run the operation on an already-exhausted structure, which is
  what made those differences measure no-ops against real work.

Not fixed, and reported as FAILED rather than as numbers: **destructive sweeps
at `medium`/`large` sizes remain build-dominated**. The number of operations
in a round is bounded by the size of the structure (you cannot pop 4096 times
from a 4096-element array and still be popping at size 4096), so the only way
to lengthen such a row is to repeat whole rounds - and every round pays the
build. The measured difference stays a small difference between two large,
noisy numbers: `dynamic_array.pop medium` calibrates to a +100 ms difference
and then produces samples at -190 ms. The reference side of the same row is
healthy (+481 ms), so this is a property of the Bend-side round, not of the
comparison.

Measuring those rows needs a round whose measured region can be lengthened
without rebuilding: for example `build; repeat r times [k pops; k pushes]`,
with the restoring pushes present in every region so that they cancel in the
difference exactly as the build does. That is a driver change on both sides
for every destructive operation and it is the first thing to do to the
harness next.

### 7c. Four C `new` references were folding a constant

`uf_new`, `bs_new`, `fw_new` and `sg_new` in `benchmarks/native/` did
`chk = mix(chk, <constant>)` and no allocation at all, while the Bend drivers
really build a one-element structure, read it and dispose of it. That is a
reference that does not implement the same operation, and it made the `new`
rows compare a Bend allocation against nothing. All four now allocate,
initialise, read and release the same one-element structure (the arena for
`union_find`, `calloc`/`free` for the other three, each matching what the rest
of that file does), folding the identical observation so the Bend and C
checksums still agree. `union_find.new` is still ~20x: Bend's allocation of
three arenas plus the record measures ~70 ns against a C bump-arena
allocation of ~4 ns, which is a real difference between the two allocators,
not a harness artefact.

### Recovery notes (iteration 0003)

* The `%E : P(_)` rewrite takes `E : {NEW == OLD}` where OLD is what occurs at
  the `_` positions in the current goal. Half of the proof debugging in this
  iteration was a missing or spurious `Equal.sym`; when the checker prints an
  `expected`/`observed` pair that differ only in that one subterm, the rewrite
  fired the wrong way round.
* A `Sigma` result cannot be bound with `+x = ...` (it is a `Type`, not
  `Data`). Follow `proofs/dynamic_array/trace.bend`: write projector `def`s
  that take the Sigma as a parameter and *re-call* the producing function for
  each projection.
* Never write a closed `SC.pow2(31n)` (or any large literal) in a type: the
  checker expands it and the machine stack overflows. Keep capacity conditions
  intensional (`Nat.is_le(n, Nat.mul(SC.pow2(B.depth_for(n)), 32n))`).
* `Word` is already a Base type name; a local word wrapper has to be called
  something else (`Wd` here).
* Matching `ALeaf`/`ANode` on a `Base.Array` works but *destroys the flat
  representation*: a structural traversal measured ~15 ns per word where an
  indexed loop measured ~0.3 ns. Always walk a `Base.Array` by index.

## Iteration 0004 (run 20260920T133039Z)

The previous iteration ended with a diagnosis: the structures that are backed
by `Base.Array` are at or near the contract, and the ones that walk retained
`&2` nodes are 3x-9x away from it, whatever the constant factors
(`### 1. The cost model of the native backend`). This iteration acted on that
diagnosis where the proof cost was payable, and measured everything again.

### 1. fenwick_tree and segment_tree: migrated to flat `Base.Array` cells

Both were trees of `Data` nodes; both are now one (fenwick) and two (segment)
flat `Base.Array`s of `U32` cells in a **split-point layout**: the value at
index `t` lives in cell `2^d + t`, and the block `[o, o + 2^p)` (p >= 1) keeps
its partial sum -- and, for the segment tree, its lazy tag -- in the cell at
its split point `o + 2^(p-1)`. The cells a block can occupy are exactly
`o+1 .. o+2^p-1`, so sibling blocks never share a cell and the frame lemmas
are interval arithmetic (`proofs/lib/flat.bend`) instead of a descendant
predicate, which is what makes the layout provable at this size.

* The old tree implementation is kept verbatim as the **proof model**
  (`proofs/fenwick_tree/model.bend`, `proofs/segment_tree/node.bend`), and the
  array walks are proved to implement exactly those functions, so none of the
  existing mathematics (prefix sums, lazy tags, the U32 wrap-around algebra)
  was re-derived. Everything is stated in shadow form
  (`proofs/<id>/state.bend`), because `Base.Array` is linear.
* Performance rule discovered while doing it: a recursive `pow2(k)` inside a
  hot walk is O(depth) per call and made every operation O(depth^2). Caching
  `base = 2^depth` in the structure and threading `h = 2^(p-1)` down the walk
  (exactly as the C reference carries `1u << (p-1)`) took `fenwick.add` from
  6x to 1.04x. The same mistake is now fixed everywhere it occurred.
* Both C references were rewritten to the same layout and both sides agree on
  the checksums of all three timed regions.

### 2. deque and queue: migrated to a windowed `Base.Array`

`deque` was two retained cons lists (a banker's deque). It is now
`DQ{depth, cap, lo, len, slots}`: the elements are the window
`[lo, lo + len)` of a block of `2^depth` slots, so element `j` is slot
`lo + j` and every end operation is one indexed read or write. A push with no
free slot at its end doubles the block -- `ANode{a, empty}` for the back,
`ANode{empty, a}` for the front, which moves every index up by the old
capacity -- so nothing is ever copied and no index arithmetic is modular.
`queue` is the same structure restricted to back-in/front-out, and its step
law is *derived* from the deque's (`proofs/queue/steps.bend`
`step_lift`/`qspec`), not re-proved.

The laws are in shadow form with one new ingredient: a push can double the
block, so `step_ok` carries the representation's capacity condition
(`depth + pushcost(op) <= 31`) and `StepOK` additionally yields
`depth(sh2) <= depth(sh) + pushcost(op)`. That is what lets the trace law
discharge the condition for a whole operation list with a single premise
`depth + (number of pushes in ops) <= 31` (`proofs/deque/trace.bend`).

Measured effect (push_back at size 4096): 11.7 ns -> 2.2 ns, 7.3x -> 2.0x;
`peek_front`/`peek_back` 3.8x -> ~1.0x; `pop_front` at large 5.5x -> 0.6x.

### 3. dynamic_array: capacity cached, to_list walks by index, reserve is lazy

Three asymptotic mistakes, all of the same family as the fenwick one:

* `capacity`, `push` and `reserve` each recomputed `pow2(depth)`, which is
  O(depth). The capacity is now a field (`DA{limit, depth, cap, length,
  slots}`) that doubles with the array. `push` 6.5x -> ~1.2x, `capacity`
  3.7x -> 0.4x.
* `reserve` also computed `2^limit` (31 doublings) on *every* call, including
  the common case where the cached capacity already suffices. The feasibility
  test now lives in the branch that needs it: 14.5x -> ~3.2x.
* `to_list` cloned the whole array and then walked it **structurally**
  (`ALeaf`/`ANode`), which the cost model says costs ~15 ns per slot. It is
  now the same indexed walk the deque uses -- no clone, no structural
  traversal: 14.6x -> 4.6x.

### 4. Disposal: releasing a `Base.Array` is dropping it

`bitset`, `fenwick_tree` and `segment_tree` released their arrays with
`burn_list(Array.to_list(a))`, which is O(capacity) and allocates a cons cell
per cell of the array. A linear `Base.Array` can simply be erased (verified
with a compiled reproducer), so `burn` is now `Unit{}` and the disposal laws
in the proofs are `{==}`. `fenwick_tree.from_list`, which disposes the old
tree, went from 12.6x to ~5.5x.

### 5. Measurement: how a size-changing row may grow

`benchmarks/run.py` lengthened a size-changing row only in whole rounds, so a
row whose build dominates (a large structure, a cheap push or pop) could not
be driven above the clock minima and was reported FAILED. It now falls back to
lengthening the batch *inside* a round when whole rounds are exhausted **or
when whole rounds have already used up the region budget** (that second case
is what made `binary_heap.push large` fail with "a single Bend region already
takes 33838ms"), and never past the row's cap. The cap is `size` for an
operation that adds elements -- the doubled region A then at most trebles the
structure -- and `size / 2` for one that removes them. Both sides do exactly
the same thing. This recovered, among others, `dynamic_array.push large`
(1.90x, measured, where it had been FAILED) and `dynamic_array.reserve large`.

### 5b. Measurement: a removal cannot be isolated by a sweep at all

The remaining FAILED rows were all removals, and their `A - B` was not merely
small but *negative by hundreds of milliseconds* (`deque.pop_back small`:
-387 ms; `dynamic_array.pop large`: -160 ms). Measured directly, the deque's
pop difference was ~1.3 ns per pop against a round that costs ~575 ns, i.e. a
signal of a few percent, and the sign came out at random.

The reason is structural, not a tuning problem: a round can only remove what
it built, so the batch is bounded by `size` while the round also pays to build
those `size` elements; and what region B does not remove inside the measured
loop it still has to deallocate at the end of the round, so part of region A's
extra work is subtracted back out. No choice of `count` and `reps` fixes
either half of that.

Every removal (`pop`, `pop_front`, `pop_back`, `dequeue`, `remove`) is
therefore now measured inside a **restoring pair**: the driver runs the
removal together with the insertion that puts the element back, so the
structure keeps its size, the batch grows in `count` like any size-preserving
row, and the build amortises to nothing. Both sides run the identical pair,
each side spelling the same key/value from the same LCG draw, and the
checksums of all three regions still agree between Bend and C (checked for
every new selector). The nanoseconds of the pair are charged to the removal,
which over-charges the Bend side by one insertion and never flatters it; every
such row carries the flag `restoring pair` in BENCHMARKS.md and `method:
"pair"` in the report.

The new selectors are `deque` 9/10, `queue` 6, `dynamic_array` 9,
`binary_heap` 7, `balanced_search_tree` 11 (remove then reinsert the SAME key,
which is size-preserving because the key stream is the built range) and
`prefix_trie` 7 (insert then remove the SAME key, which is size-preserving
because the key space is ~10^6 keys and a random key is almost never already
there). `doubly_linked_list.remove` keeps the sweep form: its rounds are not
build-dominated and it measured without failing.

Measured after the change (medians of a spot run): `deque.pop_back` 3.5 ns
against 5.9 ns of C, `deque.pop_front` 5.5 vs 6.5, `queue.dequeue` 1.20x,
`dynamic_array.pop` 1.42x-1.61x -- rows that had produced no number at all.
The tree-shaped structures stay far over the limit (`binary_heap.pop` 12.9x,
`balanced_search_tree.remove` 8.5x, `prefix_trie.remove` 6.0x as pairs), which
is the same retained-node gap their insert rows already showed; the pair form
makes them *measurable*, not fast.

### 5c. A reference handicap found while adding the pairs, and not hidden

Writing the paired C loops surfaced an asymmetry in two existing references.
Bend's `OrdMap` and `PrefixTrie` maintain their entry count and return the
previous value within the single walk the insert or remove already does; the C
drivers call `rb_find` / `tn_find` first and then `rb_insert` / `rb_remove` /
`tn_rem`, so they walk the structure twice where Bend walks it once
(`benchmarks/native/balanced_search_tree.c:28,39,63`,
`benchmarks/native/prefix_trie.c:235,257`). The reference is up to ~2x slower
than it should be on those rows, which makes the published ratios for
`balanced_search_tree.insert`/`remove` and `prefix_trie.remove` flattering to
Bend. It is not fixed in this iteration (the fix makes those ratios worse for
Bend and they are already 5x-12x over the limit, and re-measuring the whole
table costs hours); it is recorded in BENCHMARKS.md as a known bias in Bend's
favour and is a follow-up item.

### 6. What was deliberately NOT done, and why

* **binary_heap is still a Braun tree.** The operator's representation rule
  allows tree children, and a Braun tree is a genuine binary heap with
  O(log n) operations; the orchestrator's assignment asked for a packed array
  heap. Migrating it would replace 819 lines of checked Braun mathematics
  with a new development of sift-up/sift-down heap-order preservation (the
  classic "heap order holds everywhere except at one index" invariant), and
  the measured payoff is nil: with both sides on an array heap the ratio stays
  at the same 4x-6x, because the cost is Bend's per-operation overhead, not
  the representation. It is recorded here as an open item rather than done
  badly.
* **doubly_linked_list, prefix_trie, graph, balanced_search_tree** still walk
  retained `&2` nodes (an `OrdMap` node store, a trie sibling chain, an
  adjacency map of maps, a red-black tree). Moving them to `Base.Array` arenas
  is the remaining path to the contract and is worth ~50 rows, but each one is
  a full shadow-form re-proof of 1.4k-3k lines, and an arena for a structure
  whose nodes are rewired in place (not just appended) needs disjointness
  reasoning that the window and split-point layouts did not.
* **The LRU port.** Re-verified and narrowed further: flattening is transitive
  through non-recursive `Data`, so boxing the five `Word(64n)` counters in
  one-field records does not help; only a *recursive* field type escapes the
  255-slot cap. Making `Metrics` recursive is a change inside the hash-pinned
  `reference/` snapshot, and porting the reference into editable `src/` means
  carrying 22.5k lines of its proofs and 383 `Counts{...}` sites. Not done;
  the nine `lru.*` rows are still absent and the gate still fails on them.

4. **Two facts about the checker that this work established** (they matter for
   every proof in this tree, not just the heap):
   * A `~`-templated definition is only checked *at its instantiations*. At an
     abstract element type the checker accepts applications it later rejects
     at `~U32`, including hypotheses about the wrong index and linearity
     violations. Every new lemma here is therefore instantiated at U32 while
     it is written; the permanent instantiation is the one the aggregator and
     END_TO_END.bend perform.
   * `%E : P(_)` with `E : {a == b}` rewrites the marked occurrences of `b`
     into `a` (it does NOT rewrite a into b), and a proof of a function type
     can neither be marked `+` nor used twice -- which is why every invariant
     the sift loops carry is a Bool equation (`ho_exc`, `kids_le`, `lay`,
     `low_all`) rather than a universally quantified function.

     `[base, base + n)` of a power-of-two block.
   - `adj : Array<Array<U32>>` — slot i holds the adjacency block of `ids[i]`.

     renumbers an edge.

     shorter side, and at either end it moves nothing. Doubling happens on
     the side that needs room (the old block becomes the upper half when the
     front needs room), which keeps front insertion O(1) amortised.

* `min`/`max` of the red-black tree are NOT slow because of non-tail recursion.
  A tail-recursive `min_dn`/`max_dn` moved `min small` from 33.8 to 31.5 ns
  against a C walk of 1.0 ns. Reverted (not worth the proof churn).
* The `Cel` box of `segment_tree` (`CV{value: U32}`) costs almost nothing:
  Bend packs a one-field constructor over `U32` into a BUF, so `Array<Cel>` is
  a packed block, not an array of pointers. A full `Cel -> U32` rewrite moved
  `get small` 2.12x -> 2.08x and `set small` 2.37x -> 2.21x, inside the noise.
  Reverted (331 proof references for nothing). The same is true of
  `union_find`'s `Nt` and of `Maybe<U32>` slots.
* `dynamic_array.clear` cannot be fixed: the emitted `blk_new` fill writes one
  word at a time through the `u32a` device pointer type (no vectorisation), so
  filling a 262144-slot block costs 236 us against `memset`'s 15.3 us. Writing
  the block with the `[v : T^d]` literal instead of `Array.new` changes
  nothing (it is the same `blk_new`).
* Bend forbids MUTUAL recursion in live code (`law` + later `def` works only
  inside Base), a `match` may only scrutinise parameters IN THEIR DECLARATION
  ORDER, and a self-call must pass its arguments unchanged until one shrinks.
  Together these make the "open the node once per level" restructuring of
  `find` (compute the comparison from the entry just matched, instead of
  reopening the child in `c1`/`hc`) impossible: the decreasing argument would
  have to come after the changed one. That is WHY `balanced_search_tree` and
  `prefix_trie` pass the comparison down from the caller and open each node
  twice per level.
* Measured runtime floors (programs kept under `benchmarks/experiments/`,
  numbers in docs/C_EQUIVALENCE.md "Iteration 0015"):
  one shared-ADT level 13.2 ns vs one indexed-block level 1.9 ns (7x);
