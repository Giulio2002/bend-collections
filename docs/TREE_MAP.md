# Indexed red-black TreeMap

`src/balanced_search_tree.bend` now exports an owning
`TreeMap<K, V, cmp>`. Both **K and V are Data**. The comparator is a static
function and part of the map's type. It must define a consistent total order
on key-equivalence classes; the library cannot make an inconsistent comparator
valid. Custom Data records and String keys are supported.

The committed Bend module is generated by `python3 tools/generators/tree_map.py`.
That build-time source helper expands explicit state-threaded CLRS operations;
there is no runtime interpreter or code generator.

This replaces the production recursive map. The old implementation is retained
at `reference/legacy_balanced_search_tree.bend` solely with its tests/proofs and
historical benchmark. Those proofs do **not** prove the new indexed map.

## Representation and ownership

The map reuses `DynArray<&2, Node<K>>` for metadata and
`DynArray<&2, Maybe<&2, V>>` for payloads. Links are indices; zero is the black
NIL sentinel. Parent links support rotations and successor/predecessor walks.
The map caches its live size and first/last indices. Insertion and deletion
use the ordinary mirrored CLRS red-black cases.

A removed slot loses its key and payload, enters the free chain, and is reused
before growing. Capacity remains available for reuse; removal does not shrink
the allocation. `clear` clears both arrays and retains their capacity. Data
copies returned to callers may, of course, keep their referenced data alive.
There is no linked-list representation of tree entries.

Stock Bend 2.0.16 lowers these Base arrays to indexed native blocks. Composite
node reads must remain specialized through the dynamic-array return helper;
otherwise the compiler boxes the node on every read. `get_found_at` preserves
that specialization without changing dynamic-array semantics. No FFI, compiler
patches, or edits to generated C are involved.

Every operation consumes a map and returns its successor state. Iterators and
views own the map until `iterator_finish` or `view_finish` returns it. They are
backed views, not cloned collections. This replaces Java's simultaneous mutable
aliases and fail-fast checks with affine ownership.

## Public operations

All map operations start with `~K, ~V, ~cmp`; the type of the state is
`TreeMap<K, V, cmp>`. Queries also return the state.

| Operations | Result after the state | Semantics |
|---|---|---|
| `new`, `with_limit` | Map directly | Empty; optional maximum capacity exponent |
| `size`, `is_empty` | Nat / Bool | Cached size |
| `put` | Result<Rejected<K,V>, Maybe<V>> | Add or replace, returning old value |
| `put_if_absent` | Same as put | Existing value wins |
| `get`, `remove`, `replace` | Maybe<V> | Absent gives None; replace never inserts |
| `get_or_default` | V | Caller-supplied default for absent key |
| `contains_key` | Bool | Comparator-based membership |
| `contains_value` | Bool | Explicit `~eq: V -> V -> Bool`; linear scan |
| `remove_if_equal`, `replace_if_equal` | Bool | Explicit value equality; conditional change |
| `first_key`, `last_key` | Maybe<K> | Cached endpoints |
| `lower_key`, `floor_key`, `ceiling_key`, `higher_key` | Maybe<K> | Strict/inclusive predecessor/successor |
| Corresponding `*_entry` operations | Maybe<Entry<K,V>> | Data snapshots of key and value |
| `poll_first_entry`, `poll_last_entry` | Maybe<Entry<K,V>> | Remove and return endpoint |
| `clear` | Map directly | Release all entries, retain capacity |

Here `Maybe<T>` in the table means the copyable form `Maybe<&2,T>`. Put's full
status type is `Result<&2,&2,Rejected<K,V>,Maybe<&2,V>>`. A rejected insertion
returns its key/value and an error. Replacing a comparator-equivalent key keeps
the **original stored key**, matching TreeMap semantics.

## Iteration and views

`iterator`, `descending_iterator`, `entry_set`, `key_set`, and `values` return
an owning cursor. `entry_set`/`key_set`/`values` are cursor entry points, not
separately allocated collection objects. Choose `iterator_next`,
`iterator_next_key`, or `iterator_next_value` for the desired projection.
`iterator_has_next` does not advance. End of iteration returns None.

`iterator_set_value` changes the last returned entry and returns its old value;
without a current entry it returns `NoCurrent`. `iterator_remove` removes that
entry and returns its value, or None when there is no removable current entry.
A second removal cannot delete another entry. When deletion relocates an
internal successor, the cursor re-seeks its next key to avoid a stale slot.
`iterator_finish` recovers the map; `iterator_view` recovers its range view.

Bounds are `Unbounded{}`, `Inclusive{key}`, or `Exclusive{key}`:

- `sub_map(map, lower, upper)` returns an owning Result; reversed bounds return
  `InvalidView{map, InvalidBounds{}}`, preserving the original map.
- `head_map(map, upper)` and `tail_map(map, lower)` create one-sided views.
- `descending_map(map)` and `view_reverse(view)` reverse iteration/navigation.
- `view_get`, `view_contains_key`, `view_put`, `view_remove` respect the bounds.
  An out-of-range put returns `OutOfRange` and preserves the map.
- `view_first_entry`, `view_last_entry`, `view_lower_entry`, `view_floor_entry`,
  `view_ceiling_entry`, `view_higher_entry` navigate within the view. Navigation
  reverses with descending order.
- `view_size` counts the range; `view_clear` removes only entries in the range.
- `view_iterator` iterates the range; `view_finish` returns the edited full map.

This is a Bend TreeMap API, not an implementation of every Java class method.
It does not supply Java object serialization, null-key policies, clone/equals/
hashCode, callback compute/merge overloads, bulk putAll, nested range-view
intersection overloads, or concurrently usable collection-view aliases.

## Costs

With bounded-cost key comparisons: lookup/navigation/update are O(log n);
growth is O(capacity) and amortized across insertions. Cached size and endpoint
queries are O(1). Full iteration is O(n), with O(log n) worst-case individual
successor steps. Range iteration is O(log n + m). Cursor removal is O(log n),
including re-seeking after successor relocation. Range size is O(m), range
clear O(m log n), and clear O(capacity). There is no claim that these
asymptotics imply the 2.5x C performance target has been met.

## Build, test, and measure

```sh
mkdir -p build/tree-map
bend tests/tree_map/main.bend -o build/tree-map/test
python3 tools/check_tree_map.py
bend tests/tree_map/records.bend -o build/tree-map/records
./build/tree-map/records
bend TREE_MAP_COMPONENT_PROOF.bend
bend proofs/dynamic_array.bend
bend proofs/balanced_search_tree.bend  # retained LEGACY recursive proof
bend benchmarks/bend/balanced_search_tree.bend -o build/tree-map/bench
# Build the unchanged C reference with the project benchmark build first:
python3 tools/bench_tree_map.py --all
```

The record example returns `"alice=Alice:42"`. The test driver checks map
observations against an independent Python dictionary/sorted-key oracle for
ascending, reverse, and equivalence-class comparators. After each operation,
Python checks black root, no red/red edge, equal black heights, ordering,
parent links, cached endpoints/size, cleared free payloads, and an exhaustive
live/free slot partition. Arena high-water length must equal peak live size,
which checks that freed slots really are reused.

The benchmark retains the optimized C reference unchanged. Both sides fold
range/iteration output directly; neither materializes an output list. The
historical harness name `to_list` now denotes this iterator fold for TreeMap.
The reported remove workload is the same remove/reinsert pair on both sides.
Raw samples, checksums, compiler metadata, and source/binary hashes are saved.

## Proof status — incomplete

`TREE_MAP_COMPONENT_PROOF.bend` currently checks 16 explicit component laws:
empty size/get/remove, first insertion, singleton lookup/replacement/removal,
first free-slot reuse, cursor/view ownership recovery, rejecting cursor set
without a current entry, rejected view writes, and Data-array swap rejection/
single-slot success, equivalent-key retention for arbitrary singleton keys/values,
and preservation of the next iterator element after removing the first of two
entries. Three compiled semantic mutants are rejected by both the independent
tests and the component gate. The empty insertion/reuse laws quantify over arbitrary
U32 keys and values; some singleton public-query laws use key zero and
arbitrary values. They do not prove arbitrary histories.

The existing complete Data dynamic-array proof and retained recursive-tree
proof still pass. **Universal refinement and invariant preservation for the
new indexed rotations, deletion, arbitrary comparator laws, iteration, and
views remain to be proved.** Differential tests are finite evidence and are
not substituted for those missing proofs. The whole-library proof gate also
remains incomplete for pre-existing collection migrations.

## Traversal optimization (2026-09-22)

Range traversal is 1.43–1.66× faster and full iteration 1.29–1.55× faster than the prior indexed TreeMap. All six measured rows still exceed 2.5× C. Three additional local laws pass in `TREE_RANGE_PROOF.bend`; full indexed correctness and traversal equivalence remain open.
